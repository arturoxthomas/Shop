# Database migration plan: EF Core 2.1 to EF Core 10

## Current repository findings

- The web project targets .NET 10 and uses EF Core SQL Server 10.0.14.
- The repository contains four historical migrations dated 2019:
  - `20190614162222_InitialDb`
  - `20190614221312_ModifyProducts`
  - `20190629175102_Users`
  - `20190701182619_AddCountriesModel`
- `DataContextModelSnapshot.cs` was generated by EF Core 2.1.11.
- The model currently contains `Products`, `Countries`, and ASP.NET Core Identity entities. Products have a nullable `UserId` relationship to `AspNetUsers`.
- No database has been connected or changed by this repository work. The actual applied migration state, SQL Server schema, data volume, and custom database objects are not yet known.

## Safety rules

1. Do not delete or rename the historical migrations or their designer files.
2. Do not run `dotnet ef database update` against an existing database until its migration history and schema have been inspected and a verified backup exists.
3. Do not use `EnsureCreated` for a database managed by migrations.
4. Do not apply a generated migration merely because it compiles. Review every operation, especially `DropTable`, `DropColumn`, `AlterColumn`, foreign keys, indexes, and Identity changes.
5. Production schema changes should be generated as SQL, reviewed, backed up, and applied by a controlled deployment identity. The normal application identity should not have schema-owner permissions.

## Step 1 - inspect a database safely

Run `Database/Preflight-Shop.sql` against a restored copy or an approved database connection. It is read-only and reports:

- `__EFMigrationsHistory` rows and EF product versions;
- tables and columns, including SQL types and nullability;
- foreign keys and delete behavior;
- approximate row counts for Shop and Identity tables.

Save the output without exposing customer or personal data. Do not share connection strings or credentials.

## Step 2 - inspect EF's view

From the repository root, with the .NET 10 SDK installed:

```powershell
dotnet tool restore
dotnet ef migrations list --project Shop.Web --startup-project Shop.Web
dotnet ef dbcontext info --project Shop.Web --startup-project Shop.Web
dotnet ef migrations has-pending-model-changes --project Shop.Web --startup-project Shop.Web
```

The design-time factory reads `ConnectionStrings__DefaultConnection` from environment variables (or the selected appsettings environment file). For an existing database, point it only to a restored/test copy for inspection.

## Step 3 - establish the migration baseline

Compare the SQL output from Step 1 with the four historical migration operations and the model snapshot. Confirm whether the database has all four migration IDs, whether the schema matches the expected model, and whether there are manual changes not represented by migrations.

If the database's history is incomplete or its schema differs, stop and reconcile it explicitly. Do not mark migrations as applied just to make EF stop reporting them.

## Step 4 - scaffold and review an EF Core 10 migration

Only after the baseline is understood:

```powershell
dotnet ef migrations add EfCore10ModelAlignment --project Shop.Web --startup-project Shop.Web
dotnet ef migrations script --idempotent --project Shop.Web --startup-project Shop.Web --output artifacts/shop-ef10-review.sql
```

The generated migration is a candidate, not an approved deployment. Compare its Up/Down methods and SQL script against the actual schema. EF Core may detect model differences caused by the age of the EF Core 2.1 snapshot and the newer Identity/relational conventions. Do not accept broad table/column recreation without proving it is required and data-preserving.

If the generated migration is empty, verify that the live schema truly matches the current model; an empty migration alone does not prove that.

## Step 5 - validate on a restored database

1. Restore a recent backup to an isolated SQL Server database.
2. Confirm its migration history and row counts match the recorded preflight output.
3. Apply the reviewed SQL script to that restored copy only.
4. Verify login/Identity data, product ownership, country data, indexes, constraints, and application CRUD flows.
5. Compare row counts and key data before and after.
6. Repeat from a clean empty database to verify the full migration chain can create the schema.
7. Only after both paths pass should a production rollout be planned.
